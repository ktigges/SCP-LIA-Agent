Components

A bunch of these names sound like they could be the same thing -- "Security Copilot," "the agent," "the plugin," "the tools." They're not. Each one does a specific job, and none of them can do the others' jobs.

1Microsoft Security Copilot

This is a product Microsoft sells -- a chat window, like talking to ChatGPT, except built specifically for security work and able to plug into a company's actual security tools and data. For LIA, it's the thing the analyst types into. It runs the AI model, remembers the conversation, and lets us attach our own custom behavior on top.

We're using it instead of building a chat app from scratch because building a secure chat interface, connecting it to Microsoft's security data, and handling permissions correctly is a massive amount of work Microsoft already did. We're just customizing how it behaves.

2The LIA agent -- a set of instructions

A text file (agent/lia-agent.yaml) written in YAML -- a structured way to write settings and instructions, nothing scarier than a very organized to-do list. This is the rule book for the AI: always ask for a device and a time range before doing anything, only use these 8 tools, always write the final answer in this exact 10-part format. Without this file, you'd just have plain Security Copilot, which doesn't know any of LIA's specific rules.

3The Sentinel MCP plugin -- the connector

Another settings file (plugins/lia-sentinel-mcp-plugin.yaml). MCP stands for Model Context Protocol -- don't worry about the name, just know it's a standard way to give an AI a fixed list of tools it's allowed to use, and nothing outside that list. It tells Security Copilot two things: where to find the 8 approved searches, and the exact names of the 8 searches it's allowed to call. If a name isn't on that list, it can't be called -- not "shouldn't," can't.

This is the actual lock, not a polite request. Even if the AI got confused, or someone tried to trick it into doing something else, this file is what physically stops it from reaching anything beyond the 8 approved searches.

4The 8 KQL tools -- the pre-written searches

KQL is Kusto Query Language -- just a way of asking a database "show me all the records where X happened between this time and that time," like a precise search bar. These are 8 separate search queries, each written by a person ahead of time, tested, and reviewed. Each one gets saved as a tool with a plain name, like get_device_timeline, and a list of blanks it needs filled in -- which device, what time range.

The AI never sees or edits the search text. All it does is say "please run get_device_timeline for device X between time A and time B" -- filling out a form, not writing code.

The actual query files, each named for what it does: kql/normalize-time-window.kql, kql/resolve-device.kql, kql/resolve-user.kql, kql/device-timeline.kql, kql/user-authentication-timeline.kql, kql/related-alerts.kql, kql/match-observed-indicators.kql, and kql/source-coverage.kql.

5Defender XDR Advanced Hunting -- where the search actually runs

A feature inside the Microsoft Defender security portal, a website security teams already use. "Advanced Hunting" is the name of the search feature inside it, and it's the engine -- it takes one of the 8 saved searches, runs it against real data, and returns rows of results. It also enforces some of the safety rules itself, like refusing to run a search if the time range is too big.

We didn't build a separate database because all the security log data already lives here. Copying it somewhere else would be slower, more expensive, and one more place for something to go wrong.

6The actual data -- Defender and Sentinel tables

The raw information -- a giant, constantly growing spreadsheet of everything that happened: every sign-in, every file a computer opened, every alert a security tool raised. Some of it lives directly in Defender. Some lives in a connected system called Microsoft Sentinel.

LIA only sees one approved slice of this data per deployment, called a workspace -- not every workspace a company might have, just the one picked ahead of time. That keeps it obvious what LIA can see, and stops a mistake in one deployment from exposing someone else's data.

What the MCP integration gives you

Security Copilot can already write and run its own KQL on the fly, through its built-in Advanced Hunting skill. Native KQL from the model can do a lot of this -- pull a device timeline, check a sign-in history, search for an indicator. For a quick one-off question, that's often fine.

The difference shows up on the things that matter for a repeatable, auditable investigation process:

  • The query is fixed, not generated. With native KQL, the model writes new query text every time, from scratch. With MCP, the 8 queries were written once, tested, and reviewed. The model only fills in blanks like device name and time window -- it never touches the query logic itself.
  • The guardrails can't be skipped. Each of the 8 tools has limits built into the query -- a maximum 24-hour window, a check that the end time is after the start time, validation on the device or user format. Those checks run every time, regardless of what the model asks for. A hand-written query only has the limits someone remembered to add that day.
  • The tool list is enforced, not suggested. The plugin file only allows 8 named tools. If the model tries to call anything else, the call is rejected before it reaches any data. With native KQL there's no equivalent wall -- the model's judgment is the only thing standing between a normal question and an oversized or off-target query.
  • Access stays tied to the analyst. LIA runs with the signed-in analyst's own permissions, not an elevated service account. MCP doesn't change who can see what -- it just narrows what LIA is allowed to ask for within that access.

Native KQL gives the model more flexibility to write whatever query it wants. MCP gives some of that up on purpose -- the query always runs the same way, and it can't be pushed outside the 8 approved searches.

Schemas and tests

7Schemas

A rulebook for what a piece of data should look like -- which fields it needs, what type each one is. We use these to check the final report and the event data come out in the right shape. Like a form with required fields -- if something's missing, you find out before it causes a problem.

8Tests

Sample questions with expected answers, used to check LIA still behaves correctly after a change. Nobody runs these during a real investigation -- they're there to catch a mistake before it reaches an analyst.
