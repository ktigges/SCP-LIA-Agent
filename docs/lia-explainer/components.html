LIA -- Log Intelligence Assistant

How it works, explained from scratch
Overview Components Flow Guardrails Glossary

Components

1Microsoft Security Copilot

Microsoft Security Copilot provides the analyst-facing interface and orchestration for LIA. It runs the AI model, maintains the conversation, and supports custom agents and connected tools.

LIA adds investigation-specific instructions and tools to this existing security workflow, including access to Microsoft security data under the analyst's permissions.

2The LIA agent

agent/lia-agent.yaml defines LIA's workflow and behavior: the information it needs, the approved tools it can use, and the required 10-part report format.

3The Sentinel MCP plugin

plugins/lia-sentinel-mcp-plugin.yaml connects the agent to the Sentinel MCP collection. It specifies the collection endpoint and allowlists the tool names the agent can call.

Calls outside that allowlist are not available through this plugin.

4The 8 KQL tools

Each tool runs a predefined KQL query for a specific task. The queries are saved as tools with named parameters, such as the device and time range. The agent calls the tools with those parameters; it does not write or modify the query text.

The actual query files, each named for what it does: kql/normalize-time-window.kql, kql/resolve-device.kql, kql/resolve-user.kql, kql/device-timeline.kql, kql/user-authentication-timeline.kql, kql/related-alerts.kql, kql/match-observed-indicators.kql, and kql/source-coverage.kql.

5Defender XDR Advanced Hunting -- where the search actually runs

Advanced Hunting executes the saved queries against Defender and connected Sentinel data, then returns the matching records. It also enforces query limits, including the maximum time range.

This keeps investigations on the existing security data rather than copying it into a separate database.

6The actual data -- Defender and Sentinel tables

The source data consists of Defender and Sentinel tables containing records such as sign-ins, endpoint activity, and security alerts.

LIA only sees one approved slice of this data per deployment, called a workspace. The workspace is configured for the deployment, and queries run against that workspace only.

What the MCP integration gives you

LIA's MCP tools extend the telemetry available to the agent by querying approved Defender and Sentinel data that may not be exposed through its built-in tools. Each query is scoped to the entity and time range for the investigation, and returns matching records for analysis and citations. Results are limited by the analyst's permissions and the tools' row and detail limits.

The MCP approach is useful for a repeatable, auditable investigation process:

  • The query is fixed. The 8 queries are written, tested, and reviewed ahead of time. The model fills in parameters like device name and time window; it doesn't change the query logic.
  • The guardrails can't be skipped. Each of the 8 tools has limits built into the query: a 24-hour maximum for device and user investigations, 30 days for file hashes, time-order checks, and identifier validation. These checks run on every call.
  • The tool list is enforced. The plugin allowlist exposes only the approved tools for LIA. Other tools are not available through this plugin.
  • Access stays tied to the analyst. LIA runs with the signed-in analyst's own permissions, not an elevated service account. MCP doesn't change who can see what -- it just narrows what LIA is allowed to ask for within that access.

The tradeoff is less flexibility in exchange for consistent queries, bounded results, and a defined toolset.

Schemas and tests

7Schemas

Schemas define the expected fields and data types for events and investigation reports. Validation checks that outputs conform to those definitions.

8Tests

Tests run sample investigations and configuration checks to verify that LIA's behavior and outputs remain correct after changes. They run during development, not during an investigation.
